# 功能开发与学习 SOP

更新：2026-10-13。按用户明确的流程执行。当前工作入口见 [项目目录](README.md)。

以一个明确的功能范围为推进和验收单位。先讨论需求、形成 PRD 和技术架构，确认方案后开发；开发测试后提交测试文档，验收后再学习，最后汇总学习文档。

## 1. 推进顺序

```text
讨论功能需求 → 功能 PRD → 技术架构文档 → 用户确认方案
    → 开发与测试 → 测试文档 → 用户验收
    → 学习该功能 → 汇总学习文档
```

| 步骤 | 做什么 | 形成什么 |
| --- | --- | --- |
| 讨论需求 | 明确要解决的问题、期望行为、范围与约束，用具体场景澄清 | 可以写入 PRD 的需求结论 |
| 功能 PRD | 写清目标、功能要求、范围、异常行为和可观察的验收条件 | PRD.md |
| 技术架构 | 对照 PRD 设计模块、数据、接口、调用链、权限、成本和测试方案，核对现有代码 | ARCHITECTURE.md |
| 确认方案 | 向用户提供可审阅的 PRD 与技术方案，解决影响实现的待定问题 | 用户对本次具体范围和方案的确认 |
| 开发与测试 | 按确认方案实现，运行必要检查并修复问题 | 代码与真实测试产物 |
| 测试文档 | 根据实际执行写明测试范围、操作、结果、证据、成本和遗留问题 | TEST_REPORT.md |
| 功能验收 | 用户对照 PRD、测试报告和可检查结果决定是否接受 | 验收结论记入测试文档 |
| 学习功能 | 验收后，沿实际代码、调用时序与数据变化讲解，围绕用户的问题继续交流 | 实际讲解、追问和澄清 |
| 学习总结 | 学习交流结束后汇总已讲清的内容、例子、代码入口与剩余问题 | LEARNING.md |

测试计划可以在技术架构阶段写好；测试文档必须以已执行的结果为依据。自动测试或模型裁判通过不代表用户已经验收。

开发中可以回答即时问题，但正式功能学习在验收后进行。学习文档依据实际讲解与交流汇总，不能预写一份教程便宣称学习环节完成；不采用考试或强制用户说“完全理解”的方式判断学习进度。

## 2. 确认与变更

开发前需要确认具体功能 PRD 与技术架构。用户已经针对该方案明确要求实现时，视为已有确认，不重复询问。对总体方向的认可不自动代表所有后续功能或候选接口均已获开发许可。

开发后的功能验收由用户决定。用户可以接受带有明确质量项的结果；原始测试失败仍保留，不能因用户接受而改成 PASS。验收未完成时，状态写为“待验收”，正式学习阶段尚未开始。

除上述方案确认和功能验收外，不再增加开始写文档、开始测试、修复普通问题或整理资料的审批点。已确认范围内的常规实现、修复和必要复验直接推进。

需要改变已确认的范围、产品语义、权限边界或超出现有预算时，更新对应 PRD/架构并重新确认受影响部分；不必重启整个流程。设计阶段可以核查代码和研究未知接口，但不得把功能实现伪装成研究以越过确认。

## 3. 文档组织与精简

每个功能或有明确范围的阶段，最终留存四份文档，随流程逐步形成：

```text
project/
  README.md                 # 当前阶段、状态与导航
  NewWorld_PRD.md            # 项目整体产品目标
  DEVELOPMENT_SOP.md        # 本流程
  stage1/
    PRD.md                  # NPC 功能需求与行为边界
    ARCHITECTURE.md          # 技术方案、接口、当前实现
    TEST_REPORT.md           # 开发测试结果与用户验收结论
    LEARNING.md              # 验收后实际学习的汇总
```

项目总 PRD 提供产品背景，不能替代具体功能 PRD。较大的阶段可以包含多个分步交付的能力，但本次范围必须写清，并按同一顺序完成确认、开发、测试、验收和学习；不能以整个阶段早已讨论为由跳过具体方案确认。

阶段尚未走到测试或学习时，不提前编造报告或总结，也不要求目录一开始就凑齐四份文件。小修改更新对应文档，不再额外建立背景、需求拆解、独立开发日志或重复规格。

PRD 维护“需要什么”，架构维护“如何实现”，测试文档维护“实际验证与验收结果”，学习文档维护“这次学习弄清了什么”。各自只引用其他文档，不复制成另一份主记录。现行设计正文保持最新，重要变化用简短日期和理由说明；测试原始结果按日期保留。

使用 UTF-8 与相对链接。文档开头注明日期、范围和状态。合并删除旧文件前保留仍有效的需求、实现约束、测试证据和已有学习内容，再同步 README、AGENTS 与全部受影响引用。运行产物留在被 Git 忽略的 reports/，不把大段 trace 复制进文档。

## 4. 测试和费用

检查约定见 [AGENTS.md](../../AGENTS.md)，现有测试入口与历史结果见 [Stage 1 测试报告](stage1/TEST_REPORT.md)。

- 纯文档变更检查链接、状态与内容一致性；代码或行为变更执行类型检查、工程测试和 scripted 场景，组合入口为 npm run check。
- 新行为随实现交付 fixture、明确成功条件及相应检查。权限、状态、预算和取消由程序判断；开放语义由相关 live 场景验证，硬性失败不能被语义评分覆盖。
- 影响真实模型行为且配置可用时，按有限预算运行相关 live；每个 trial 独立初始化，保留全部 PASS、FAIL、ERROR，不重生成挑选满意样本。
- 技术方案明确产品运行的请求、工具、token、超时和整轮限制；试验前明确场景数、trial 数及请求上限。角色、世界裁定与评测模型分别计数，价格未知时不编造金额。
- 测试报告记录实际版本、配置摘要、执行命令、判定、证据入口、预算与缺口，省略凭据。通过后不无理由扩大或重复验证。

## 5. 当前资料的衔接

Stage 1 的 [PRD](stage1/PRD.md) 整理总体 NPC 功能需求，[架构](stage1/ARCHITECTURE.md) 区分已实现部分与规划。六类能力方向已获认可，但下一项新增功能的范围和具体技术方案仍待讨论与确认。

首个受控回应能力已有用户完成确认、测试证据和学习资料，历史事实继续有效，不为套用新流程重新审批。现有 [学习文档](stage1/LEARNING.md) 仅合并这一能力的既有资料，不表示完整 Stage 1 已验收或学习完成。后续新增功能按本流程推进。
